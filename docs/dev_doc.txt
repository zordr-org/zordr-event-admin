1. Introduction & Purpose
This document specifies the technical design and development plan for the Zordr Admin Portal — the internal back-
office application used by Zordr's own team to operate the marketplace: approving organizers, moderating events 
before they go live, overseeing orders/settlements/refunds, running customer support, tracking platform analytics, 
and managing internal employee access.
It is derived from the 16-screen UI reference set (Login, Dashboard, Organizers list + detail, Events list + Review, 
Orders, Customers, Settlements, Refunds, Support, Analytics, Employees, Manage Roles, Create Role, Settings) and 
translates that UI into functional behaviour, data model, technology stack, architecture, API design, and 
business/validation rules.
This is the third and final leg of the Zordr platform alongside the Organizer Portal and the Customer App. It is the 
control-plane that sits above both: organizer onboarding submitted in the Organizer Portal is approved here; events 
published by organizers pass through a moderation gate here before becoming visible in the Customer App; and 
orders/settlements/refunds generated by the other two modules are all reconciled and, where needed, overridden 
here.

4. Functional Specification by Screen
4.1 Admin Login
● Email + password only (no OTP/SSO, consistent with a small, tightly controlled internal user base).
● Explicit "Authorized personnel only — all access is monitored and logged" notice — implies mandatory audit 
logging of every login and, ideally, every privileged action taken afterward.
Tech rule: failed login attempts should be rate-limited/lockout-protected; every successful login should write an 
AuditLog entry (actor, IP, device, timestamp) given the stated monitoring posture.
4.2 Dashboard
● KPI cards: Today's GMV, Today's Registrations, Active Events, Pending Approvals (events & organizers combined), 
Failed Payments, Refund Requests, Live Events, Pending Settlements — each with a day-over-day delta.
● Trend charts: Daily Revenue (GMV), Registrations, Platform Growth (Events vs Customers) — selectable time 
range.
● Recent Activity — a unified, platform-wide event log (organizer onboarded, event created, ticket sold, refund 
requested, settlement completed, event published, support ticket, payment failed) with type, detail, user, and 
status.
● Live Events ticker — currently-running events with live attendance counts.
● Quick Actions — Approve Organizer, Approve Event, Issue Refund, Create Admin.
Tech rule: this dashboard aggregates across the entire platform (all organizers/events), unlike the Organizer Portal's 
dashboard which is scoped to one organizer — it must be backed by a platform-wide aggregation/reporting service 
(e.g. a data warehouse or materialized views), not a naive join across live transactional tables, to stay performant at 
scale.

4.3 Organizers — List & Detail
● List: KPI strip (Total/Approved/Pending/Rejected/Blocked), searchable/filterable table (status, KYC status, city) 
with per-organizer active events and total revenue, row actions.
● Detail — tabs: Overview, Documents, Bank & GST, Events, Revenue, Settlements, Support Tickets, Notes.
● Overview shows org identity, primary contact, org info, lifetime stats, recent events/settlements/support tickets.
● Actions: Update Organizer, Send Message, Suspend Organizer, Reject Organizer, Reset Password, and an internal 
Quick Notes / Recent Notes log.
Tech rule: this is the approval authority for the Organizer Portal's onboarding submission (Organizer Portal §4.2) — 
an organizer's KYC/Approved status is written here, not self-service; Suspend/Reject must immediately cascade to 
block that organizer's ability to publish/edit events and receive payouts. All admin notes and status changes are 
timestamped and attributed to the acting employee (audit trail).
4.4 Events — List & Review
● List: KPI strip (Total/Published/Pending Review/Completed/Cancelled), filterable table with a distinct "Pending 
Review" status row action ("Review") versus "View" for already-published events.
● Event Review screen: full read-only render of the organizer's submitted event (banner/gallery, description, 
venue+map, schedule, tickets & pricing, organizer info, policies, terms) alongside a Review Checklist (banner & 
images / details & description / date-time-venue / ticket types & pricing / organizer info / policies & terms / 
content guidelines) that must be fully checked.
● Actions: Preview as Customer, Send Back (to organizer with notes), Reject, Approve & Publish; an Admin Notes 
field and a Previous Review Activity audit trail (submitted for review, event created, by whom, when).
Tech rule: this is the moderation gate implied but not visible in the Organizer Portal's own Publish step (Organizer 
Portal §4.5 Step 7) — an event's true lifecycle is therefore Draft → Submitted (by organizer) → Pending Review 
(admin queue) → Published (admin-approved) / Sent Back / Rejected, not simply Draft → Published as the organizer-
side document alone would suggest. The Customer App's discovery/search must only ever surface events in the 
Published state. Send Back should reopen the event for organizer editing while preserving the submitted version for 
reference/diff.
4.5 Orders
● KPI strip (Total/Paid/Pending/Failed/Refunded Orders with success rate), rich filter set (event, organizer, payment 
status, order status, date range), Export and Bulk Actions.
● Table: Order ID, Customer, Event, Organizer, Amount, Tickets, Payment Gateway, Payment Status, Order Status, 
Created At.
Tech rule: this view is a read/administrative-action layer over the same Order/Ticket entities used by the Customer 
App and reported in the Organizer Portal's Settlements — it must never be a separate copy of order data. Bulk 
Actions (e.g. bulk refund, bulk export) must be queued/async for large selections and fully audit-logged given the 
financial sensitivity.
4.6 Customers
● KPI strip (Total/Active/New This Month/Repeat/Banned-Blocked Customers), searchable/filterable table with 
Events Attended, Lifetime Spend, Last Order, Status, Joined On.
● Row actions presumably include block/unblock and view detail (mirrored pattern from Organizers).
Tech rule: 'Events Attended' and 'Lifetime Spend' must be computed the same way as in the Customer App's own 
Profile screen (CheckIn-derived attendance, captured-order-derived spend) so the two surfaces never disagree; 
Blocked customers must be prevented from completing new checkouts platform-wide, not just flagged for display.

● KPI strip (Total/Paid/Pending/On Hold Settlement Amounts), tabs (All/Pending/Paid/On Hold/Failed), filterable 
table: Organizer, Event(s), Settlement Period, Gross Sales, Platform Fee (shown here as 5%), Gateway Fee, 
Refunds, Net Payout, Status, Transfer Date.
● Generate Settlement and Download Report actions; a Settlement Policy footer ("payouts initiated within 5–7 
business days from end of settlement period, subject to no pending refunds/disputes").
Tech rule / reconciliation flag: the Platform Fee is displayed here as 5%, while the Organizer Portal's Create-Event 
Tickets step discloses "2% + ₹5/ticket" to organizers. These must be reconciled into a single authoritative fee-
configuration source before development — either the two are genuinely different fee lines (e.g. a 2% payment-
processing pass-through disclosed to organizers at checkout time vs. a blended 5% platform commission booked 
internally) or one figure is stale; whichever it is, both the Organizer Portal and this screen must read from the same 
FeeConfig entity, not independently hardcoded values. Settlement generation should remain a scheduled, 
idempotent batch process (as specified in the Organizer Portal document §9.5), with this Admin screen providing 
oversight/override (Generate, Hold, mark Failed) rather than ad hoc manual computation.
4.8 Refunds
● KPI strip (Total/Processed/Pending/Rejected Refunds), filterable table: Refund ID, Order ID, Customer, Event, 
Amount, Reason, Status, Requested On, Processed On, with a "Review" action for Pending items and "View" for 
resolved ones.
● Refund Policy footer (5–7 business days processing after approval).
Tech rule: approving a refund here must trigger the same automated gateway-refund + notification workflow 
described for organizer-initiated cancellations (Organizer Portal §9.6) and must correspondingly adjust the relevant 
Settlement's Net Payout if the refund lands within an open settlement period.
4.9 Support
● KPI strip (Total/Resolved/Open Tickets, Avg. Response Time), filterable table across both organizer and customer-
originated tickets, with Category, Event, Status, Priority.
● Sidebar: Ticket Categories breakdown, Quick Actions (Create Ticket, View FAQs, Support Inbox, Live Chat), and 
Support SLA panel (first response < 6 hours, resolution < 24 hours, CSAT 4.7/5).
Tech rule: SLA timers (first response, resolution) must be computed and monitored server-side against ticket-created 
and first-reply timestamps, with alerting when a ticket is at risk of breaching SLA — this is an operational monitoring 
requirement, not just a display metric.
4.10 Analytics
● Platform-wide KPI strip (Total GMV, Orders, Tickets Sold, Active Events, Unique Customers, Conversion Rate).
● Charts: GMV Trend, Orders vs Customers, Revenue by Payment Method (donut), Order Status Distribution 
(donut), Settlement Overview (donut), User Growth.
● Ranked tables: Top Events by Revenue, Top Organizers by GMV, Customers by City.
● Download Full Report action and a narrative Insight callout.
Tech rule: given the volume of cross-cutting aggregation (by event, organizer, city, payment method, time), this 
screen should be backed by a dedicated analytics/OLAP layer (e.g. scheduled ETL into a reporting schema or 
warehouse) rather than live queries against the transactional Postgres tables also serving checkout traffic, to avoid 
analytics load degrading production performance.
4.11 Employees, Manage Roles, Create Role
● Employees: KPI strip (Total/Active/Inactive Employees), table (Name, Email, Role, Department, Status, Last Active), 
inline "Add New Employee" panel (name, email, role, department, send-invitation toggle) with a live Role 
Permissions Preview.
● Manage Roles: role list (system + custom) with employee counts, and a permission matrix 
(View/Create/Edit/Delete/Export) per module for the selected role, editable and savable.

● Create Role: role name/description/type (System vs Custom Role), full module permission grid with Select Preset /

Tech rule: the permission matrix here (module × View/Create/Edit/Delete/Export) is the literal authorization schema

4.12 Settings
● Tabs: General, Users & Access, Notifications, Payments, Platform, Security, Integrations.
● General: platform organization details (name, support email, contact, address, logo), Preferences (timezone,

Tech rule: 'Delete Organization' here refers to the Zordr platform tenant itself (catastrophic, presumably reserved for 
a multi-tenant SaaS future or a decommissioning path) — it must be gated far more strictly than any other 
destructive action in the system (e.g. Super-Admin-only, secondary confirmation, possibly requiring Zordr leadership 
sign-off outside the UI itself).

7. System Architecture (High Level)
● Client tier — Next.js Admin Portal (desktop-first), served over a VPN-restricted or IP-allowlisted domain distinct 
from the public Organizer/Customer domains, given its access to PII and financial data.
● API tier — Shared NestJS API; Admin-scoped endpoints live under their own module namespace, enforced by the 
centralized RBAC guard described in §4.11 and §6.
● Moderation workflow — The Event publish pipeline becomes: Organizer Portal writes Event.status = Submitted → 
EventReview record created → Admin Review screen → Approve sets Event.status = Published (visible to 
Customer App) / Send Back reopens for organizer edits / Reject terminates the submission with a reason.
● Reporting tier — A CDC/ETL pipeline replicates Order/Settlement/Event/User data into a reporting store for 
Dashboard and Analytics, so heavy aggregate queries never compete with live checkout traffic on the primary 
database.
● Audit tier — Every mutating admin action (approve/reject/suspend/refund/role-change/settings-change) writes to 
an append-only AuditLog, ideally via a database trigger or an interceptor at the API layer so it cannot be bypassed 
by a future code path.

9. Business & Validation Rules ("Tech Rules")
9.1 Access & Security
● Admin accounts are provisioned only via the Employees → Add Employee flow (invite-based), never self-service 
signup.
● System roles (Super Admin, Event Manager, Operations Manager, Support Executive, Finance Executive, 
Marketing Executive) are protected from deletion; only their permission grants can be edited.
● Every login and every mutating action is written to AuditLog with actor, timestamp, IP, and a before/after diff 
where applicable, per the Login screen's stated monitoring policy.

9.2 Organizer Governance
● Organizer KYC status transitions (Pending → Approved/Rejected, Approved → Suspended) are admin-only actions; 
an organizer cannot self-approve or self-reinstate.
● Suspending or rejecting an organizer must immediately cascade: their events are unpublished/hidden from 
discovery, and any pending settlement to them should move to On Hold pending review.
9.3 Event Moderation
● An event cannot reach Published status without passing through EventReview with all checklist items satisfied and 
an explicit Approve & Publish action; Send Back and Reject both require a reason, which is relayed back to the 
organizer.
● The Customer App's public discovery/search index must only include events with Event.status = Published — 
Pending Review and Sent-Back events are never publicly queryable, even via direct link.
● Re-submission after Send Back re-enters the review queue as a new EventReview cycle, preserving the prior 
cycle's history for audit.
9.4 Orders, Settlements & Refunds
● The Admin Portal must never maintain a divergent copy of Order/Settlement data from the Organizer Portal or 
Customer App — all three read the same tables via role-scoped queries.
● The platform fee percentage used in any settlement calculation must be read from a single FeeConfig source; the 
current discrepancy between the Organizer-facing 2%+₹5/ticket disclosure and the Admin-facing 5% figure (§4.7) 
must be resolved into one authoritative model before this module ships, since it directly affects money owed to 
organizers.
● Refund approval here must trigger the same idempotent gateway-refund workflow as an organizer- or attendee-
initiated refund, and must adjust the affected settlement's Net Payout if that settlement period is still open.
● Bulk order actions (bulk refund, bulk export) on large selections must be processed asynchronously with a job-
status indicator, not a blocking synchronous request.
9.5 Support & SLAs
● First-response and resolution SLA timers start at ticket creation and are computed server-side; 
approaching/breached SLAs should trigger internal alerts (e.g. Slack/email to the assigned team), not just a passive 
dashboard number.
9.6 RBAC Enforcement
● Every module's View/Create/Edit/Delete/Export actions are individually gated; an employee with only 'View' on 
Settlements, for example, must not be able to hit the Generate Settlement or Export endpoints even if they know 
the URL.
● Deleting a role that still has assigned employees should be blocked (or require reassigning those employees first) 
to avoid orphaned access states.
10. Security & Compliance
● This portal is the highest-privilege surface in the platform (PII, bank details, payment data, ability to 
publish/unpublish events and move money) — it should sit behind additional network-level protection (VPN/IP 
allowlist) beyond standard TLS, and MFA should be strongly considered even though not shown in the current 
screens.
● Field-level encryption for any bank/payout data viewed here mirrors the Organizer Portal's requirement (§10 of 
that document); admins should see masked account numbers by default with an explicit reveal-and-log action for 
full details.
● Full audit trail (per §9.1) is the primary compliance control for an internal tool with this level of access, and should 
be immutable (append-only, ideally shipped to a separate log store an admin cannot edit).

● Data-access minimization: roles like Marketing Executive or Support Executive should see only the customer/order
